## 5교시 · SOAR 와 플레이북 4요소 이해하고, 알림 두 건을 수동 처리해 보기

### 문제 5-1 · 경로 스캔 플레이북을 쓰고, 알림 두 건을 수동 처리하기

- (가) 내가 쓴 PB-003 의 액션과 승인을 적고, 5번 확인 명령의 출력을 붙여 넣어 주세요.
  - 쓸 내용: ① PB-003 의 액션 ② PB-003 의 승인 ③ 확인 명령의 출력(코드 상자에 붙여 넣기)
  - 답: ① 액션은 `IP 차단` · `티켓 생성` 이다. ② 승인은 `담당자 승인 필요` 이다. ③ 확인 명령의 출력은 아래와 같다(INC-001 은 `dami` 잠금 + TCK-1, INC-005 는 담당자가 허락했다고 가정하고 `198.51.100.90` 차단 + TCK-2).

```
['dami'] ['198.51.100.90'] 2
```

- (나) 🔍 알림 두 건을 수동 처리하면서 `system_state.json` 을 직접 고친 곳이 모두 몇 군데였는지 적고, 알림이 100건이면 어떤 문제가 생길지 적어 주세요.
  - 쓸 내용: ① 고친 곳의 개수 ② 알림이 100건일 때 생길 문제
  - 답: ① 모두 4군데다. `locked_users` 에 `"dami"` 1군데, `blocked_ips` 에 `"198.51.100.90"` 1군데, `tickets` 에 TCK-1 · TCK-2 두 건 2군데다(처음에는 `tickets` 를 한 군데로 세어 3군데라고 썼다).
    ② 알림 두 건에 4군데이니 알림이 100건이면 수백 군데를 손으로 고쳐야 한다. 같은 모양의 줄을 반복해 쓰다 보면 쉼표나 대괄호를 빠뜨려 파일이 깨지기 쉽고, 티켓 번호(TCK-1, TCK-2 …)도 사람이 직접 세어야 해서 겹치거나 건너뛰기 쉽다. 어떤 알림을 처리했고 어떤 알림을 빠뜨렸는지도 남지 않아서, 빠뜨린 알림이 있어도 아무도 알 수 없다.

- (다) 🔍 PB-003 의 승인 값을 그렇게 정한 이유를 적어 주세요. 대상이 사용자 계정이 아니라 IP 라는 점과 잘못 차단했을 때의 영향을 근거로 쓰세요.
  - 쓸 내용: ① 승인 값 ② 대상이 IP 라는 점을 근거로 한 이유 ③ 잘못 차단했을 때의 영향
  - 답: ① 승인 값은 `담당자 승인 필요` 다. 자동으로 바로 차단하지 않고, 담당자가 확인하고 허락한 뒤에 차단한다.
    ② 사용자 계정은 한 사람에게 대응하지만, IP 는 한 사람과 1:1 로 대응하지 않는다. 회사 · 학교의 NAT, 공용 와이파이, 프록시 · VPN, 클라우드 공유 IP 처럼 IP 하나 뒤에 여러 사용자가 있을 수 있다. 반대로 공격자는 IP 를 쉽게 바꿀 수 있어서, 탐지된 IP 가 실제 공격자의 것인지 공격자가 거쳐 간 정상 시스템의 것인지 자동 판단만으로 확신하기 어렵다. 그래서 차단 전에 사람이 IP 의 주인 · 평판 · 내부나 협력사 대역인지를 확인하는 단계가 필요하다. 게다가 `198.51.100.90` 은 30점 `low` 등급이고 요청 3개가 모두 실패였으므로, 급하게 막지 않아도 담당자가 확인할 시간을 두는 쪽이 안전하다.
    ③ IP 를 잘못 차단하면 계정 하나가 잠기는 것보다 피해 범위가 훨씬 넓다. 그 IP 를 쓰는 정상 사용자 전체가 접속하지 못하고, 협력사나 결제 · API 연동 서버, 모니터링 시스템의 IP 라면 서비스 장애나 업무 중단으로 이어진다. 차단 정책은 여러 시스템에 한꺼번에 적용되므로 원인을 찾아 풀 때까지 피해가 이어진다. 대응이 조금 늦어지더라도 승인 단계를 두어 잘못된 차단의 위험을 줄이는 것이 맞다고 판단했다.

## 6교시 · 플레이북으로 알림 5건을 한 번에 처리하고 감사 기록 남기기

### 문제 6-1 · 플레이북 실행기로 알림 5건 처리하고 감사 기록 읽기

- (가) 실행한 출력 전체를 붙여 넣고, 실행 후 잠긴 계정 · 차단한 IP · 티켓의 개수와 승인 대기 건수를 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 잠긴 계정 ③ 차단한 IP ④ 티켓 수 ⑤ 승인 대기 건수
  - 답: ② 잠긴 계정은 `dami` 1개 ③ 차단한 IP 는 0개 ④ 티켓은 1건(TCK-1) ⑤ 승인 대기는 2건(INC-002 · INC-005)이다.

```
--- 단계 1: 불러온 인시던트 5 건 · 등록된 플레이북 3 개
--- 단계 2: 실행 전 모의 시스템 상태
잠긴 계정: []
차단한 IP: []
티켓: 0 건 · 담당자 알림: 0 건
--- 단계 3: 인시던트마다 플레이북 실행
INC-001 dami high -> PB-001 실행 완료 (상태: 조치됨)
INC-002 seoyeon mid -> PB-002 승인 대기 (상태: 분류됨)
INC-003 gaeun mid -> 맞는 플레이북 없음 (상태: 탐지됨)

차단한 IP: []

--- 단계 5: 승인 대기 2 건
INC-002 seoyeon PB-002 · 담당자 승인 필요

--- 단계 6: 감사 기록 4 건을 action_log.json 에 저장
INC-001 PB-001 계정 잠금 : 계정 dami 잠금 완료
INC-001 PB-001 티켓 생성 : 티켓 TCK-1 생성
INC-002 PB-002 전체 : 승인 대기
INC-005 PB-003 전체 : 승인 대기
```

- (나) 🔍 5교시에서 INC-005 를 수동 처리할 때와 달리, 실행기는 INC-005 를 어떻게 처리했는지 적어 주세요. 근거는 단계 3 · 4 · 5 의 출력으로 쓰고, 그렇게 처리한 이유도 적어 주세요.
  - 쓸 내용: ① 실행기가 INC-005 를 처리한 방식 ② 단계 3 · 4 · 5 에서 찾은 근거 ③ 그 이유
  - 답: ① 5교시에 수동으로 처리할 때는 담당자가 허락했다고 가정하고 `198.51.100.90` 을 바로 차단했다. 실행기는 INC-005 에 PB-003 을 맞췄지만 차단은 실행하지 않고, 승인 대기로 멈춰 담당자의 판단을 기다리게 했다.
    ② 단계 3: `INC-005 198.51.100.90 low -> PB-003 승인 대기 (상태: 분류됨)`. 플레이북은 찾았지만 실행 완료가 아니라 승인 대기이고, 상태도 `조치됨` 까지 가지 않고 `분류됨` 에 머물렀다.
       단계 4: 실행 후에도 `차단한 IP: []` 가 비어 있다. 실제 차단이 일어나지 않았다.
       단계 5: 승인 대기 목록에 `INC-005 198.51.100.90 PB-003 · 담당자 승인 필요` 가 있다. 내가 PB-003 에 정한 승인 값 때문에 멈춘 것이다.
    ③ `run_playbook` 이 플레이북의 `approval` 이 `자동` 이 아니면 액션을 하나도 실행하지 않고 「승인 대기」로 기록한 뒤 끝나기 때문이다. PB-003 의 대상은 계정이 아니라 IP 라서 잘못 차단하면 피해가 넓고, INC-005 는 `low` 라 몇 분 늦게 대응해도 위험이 크지 않으므로 사람이 확인한 뒤 실행하도록 정한 대로 동작했다. 수동 처리에서는 사람이 이 확인을 기억해야 했지만, 실행기는 매번 확인해서 판단(승인)과 실행을 나눈다.

- (다) 🔍 감사 기록(단계 6)에서 INC-002 의 한 줄을 읽고, 그 인시던트에 실제로 무엇이 일어났고 무엇이 일어나지 않았는지 적어 주세요. 이런 기록이 현업에서 필요한 이유도 적어 주세요.
  - 쓸 내용: ① INC-002 에 일어난 일 ② 일어나지 않은 일 ③ 기록이 필요한 이유
  - 답: ① `INC-002 PB-002 전체 : 승인 대기` 한 줄로 보아, seoyeon(mid)의 인시던트에 PB-002(대량 다운로드)가 맞아서 시작됐다. PB-002 는 `담당자 승인 필요` 라서 플레이북 전체가 승인 대기로 기록됐고, 상태는 `탐지됨` 에서 `분류됨` 으로 바뀌었다.
    ② PB-002 의 액션(`담당자 알림` · `티켓 생성`)은 하나도 실행되지 않았다. INC-001 처럼 액션별 기록 줄이 없고, 단계 4 에서도 티켓은 INC-001 의 TCK-1 한 건뿐이며 담당자 알림은 0건이다. 승인을 요청하는 알림조차 나가지 않았으므로, 담당자가 승인 대기 목록을 따로 보지 않으면 이 인시던트는 그대로 멈춰 있게 된다.
    ③ 책임 추적: 사고가 난 뒤 「그때 왜 조치하지 않았나」를 물으면 이 기록으로 「승인을 기다리고 있었다」고 설명할 수 있다. 기록이 없으면 실행하지 않은 일은 아무 흔적도 남지 않는다.
       누락 방지: 「승인 대기」처럼 멈춘 건이 남아야 담당자가 놓치지 않고 후속 처리를 한다.
       감사 · 규정 준수: 보안 조치는 누가 · 언제 · 어떤 근거로 실행하거나 보류했는지 증빙을 요구받는 경우가 많다(ISMS-P 등).
       개선 근거: 기록을 모아 보면 승인 대기가 자주 걸리는 플레이북, 맞는 플레이북이 없는 인시던트(INC-003 · INC-004) 같은 빈 곳이 보여 플레이북을 고칠 수 있다.
