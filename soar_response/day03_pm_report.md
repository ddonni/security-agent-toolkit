## 5교시 · 기록을 보고 자동이 바꾼 것만 되돌리고, 되돌릴 수 없는 조치는 따로 표시하기

### 문제 5-1 · 기록을 보고 자동이 바꾼 것만 되돌리기

- (가) 실행한 출력 전체를 붙여 넣어 주세요. 그리고 단계 5 의 잠긴 계정과 차단한 IP 를 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 단계 5 의 잠긴 계정 ③ 단계 5 의 차단한 IP
  - 답: 단계 5의 잠긴 계정은 `['junho']`이고, 차단한 IP는 없다(`[]`).

```
--- 단계 1: 4교시가 남긴 파일
잠긴 계정: ['junho', 'dami']
조치 기록: 5 건
차단한 IP: ['198.51.100.90']
--- 단계 2: INC-001 은 오탐으로 확인됨 — 되돌리기
INC-001 dami · 되돌리기 불가 · 세션 2개 → 세션 0개 · 되돌릴 수 없는 조치(세션 종료) — 사용자가 다시 로그인해야 함
INC-001 dami · 계정 해제 · 잠김 → 잠기지 않음 · 되돌리기: 퇴사한 계정의 서버 요청
--- 단계 3: INC-006 도 오탐으로 확인됨 — 되돌리기
INC-006 junho · 되돌리기 불가 · 세션 1개 → 세션 0개 · 되돌릴 수 없는 조치(세션 종료) — 사용자가 다시 로그인해야 함
--- 단계 4: INC-005 도 오탐으로 확인됨 — 되돌리기
INC-005 198.51.100.90 · IP 해제 · 차단됨 → 차단되지 않음 · 되돌리기: 경로 스캔 (120분 뒤 자동 해제)
--- 단계 5: 되돌린 뒤 상태
잠긴 계정: ['junho']
차단한 IP: []
```

- (나) 🔍 INC-006 의 `junho` 는 단계 3 에서 계정이 해제되지 않았고 단계 5 에도 잠겨 있습니다. 4교시 기록의 `before` 와 `after` 를 근거로 이유를 적고, `should_undo` 의 5 · 6번이 없었다면 어떤 일이 생겼을지 적어 주세요.
  - 쓸 내용: ① 4교시 기록에서 `junho` 의 `before` · `after` ② 해제되지 않은 이유 ③ 5 · 6번이 없을 때 생기는 일
  - 답: ① 4교시 기록에서 `junho`의 계정 잠금은 `before`가 `잠김`, `after`가 `잠김`이다(`INC-006 junho · 잠김 → 잠김 · 이미 잠겨 있어 변경 없음`).
    ② `junho`는 자동 대응 전부터 잠겨 있던 계정이라 조치 전과 후가 같다. `should_undo`의 5번 `if record["before"] == record["after"]:`가 참이 되어 6번에서 False를 리턴했고, 되돌릴 대상에서 빠졌다. 자동 대응이 바꾼 것이 없으니 되돌릴 것도 없다.
    ③ 5 · 6번이 없으면 `junho`의 기록도 「계정 잠금」이라 `UNDOABLE_ACTIONS`에 걸려 해제된다. 자동 대응과 상관없이 원래 잠겨 있던 계정(이미 퇴사 처리된 계정)이 오탐 복구 과정에서 풀려 버려, 막혀 있어야 할 계정이 다시 쓸 수 있는 상태가 된다.

- (다) 🔍 단계 2 의 `되돌리기 불가` 줄이 나온 이유를 적어 주세요. 또 세션 종료를 기록에 남기지 않고 「모두 원래대로」라고만 보고하면 어떤 문제가 생길지 적어 주세요.
  - 쓸 내용: ① `되돌리기 불가` 줄이 나온 이유 ② 기록하지 않고 「모두 원래대로」라고 보고할 때의 문제
  - 답: ① `INC-001 dami · 되돌리기 불가 · 세션 2개 → 세션 0개 …` 줄은 세션 종료 기록이 `before`와 `after`가 다르지만(실제로 바뀌었지만) `UNDOABLE_ACTIONS`(`계정 잠금` · `IP 차단`)에 없는 조치라서 나왔다. 끊긴 세션은 해제 한 번으로 다시 살릴 수 없고 사용자가 다시 로그인해야 하므로, 되돌리지 않고 「되돌리기 불가」로 따로 기록했다.
    ② 「모두 원래대로」라고만 보고하면 보고와 실제 상태가 달라진다. 계정은 풀렸지만 세션은 끊긴 채라 `dami`는 다시 로그인해야 하는데, 사용자가 문의해도 세션을 끊었다는 기록이 없어 담당자가 원인을 찾지 못한다. 사람이 이어서 안내해야 할 일도 빠진다.

## 6교시 · 알림 8건을 판단 → 조치로 처리하고, 기록을 요약해 확인 목록 만들기

### 문제 6-1 · 알림 8건을 처리하고 기록을 요약해 확인 목록 만들기

- (가) 실행한 출력 전체를 붙여 넣어 주세요. 그리고 단계 3 의 요약과 단계 4 의 건수를 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 단계 3 의 요약 ③ 단계 4 의 건수
  - 답: 단계 3의 요약은 `{'변경됨': 2, '변경 없음': 2, '확인 실패': 1}`이고, 단계 4의 담당자 확인이 필요한 건은 4건이다.

```
--- 단계 1: 알림 8건 처리

INC-003 gaeun -> 승인 대기 (조치 기록 0건)
INC-004 jiwoo -> 오탐 종료 (조치 기록 0건)
INC-005 198.51.100.90 -> 조치 실패 (조치 기록 1건)

--- 단계 3: 근무 보고 요약
{'변경됨': 2, '변경 없음': 2, '확인 실패': 1}
잠긴 계정: ['junho', 'dami']

--- 단계 4: 담당자 확인이 필요한 건

INC-010 gaeun : VIP 계정이라 담당자 승인이 필요함
INC-005 198.51.100.90 : 조치 후 확인 실패 — 방화벽 연결 실패
```

- (나) 🔍 INC-005 는 `조치 실패` 로 나왔고 요약의 `확인 실패` 가 1 입니다. 단계 2 의 줄을 근거로 이유를 적고, 6번(`is_failure`, 확인 실패인지 구하는 함수)이 없다면 이 건이 근무 보고에서 어떻게 보일지 적어 주세요.
  - 쓸 내용: ① INC-005 가 `조치 실패` 인 이유(단계 2 의 줄) ② 6번이 없을 때 근무 보고에서 보이는 모습
  - 답: ① INC-005는 `FIREWALL_DOWN_FOR`에 있어서 방화벽 연결이 끊긴 상황으로 처리됐다. 단계 2의 `INC-005 198.51.100.90 · IP 차단 · 차단되지 않음 → 차단되지 않음 (확인 실패) · 방화벽 연결 실패` 줄처럼 `after`에 「확인 실패」가 들어 있어 `is_failure`가 참이 되었고, 확인 실패 1건으로 셌다.
    ② 6번이 없으면 `is_failure`가 값을 리턴하지 않아(None, 거짓 취급) 확인 실패로 걸러지지 않는다. 그러면 `before`(`차단되지 않음`)와 `after`(`차단되지 않음 (확인 실패)`)의 글자가 달라서 「변경됨」으로 세어지고, 요약이 `{'변경됨': 3, '변경 없음': 2, '확인 실패': 0}`이 된다. 실제로는 차단되지 않은 IP가 차단된 것처럼 보고되고, 단계 4 확인 목록에서도 빠져 아무도 다시 차단하지 않는다.

- (다) 🔍 INC-008 과 INC-009 는 모두 차단되지 않았습니다. INC-008 은 승인 대기이고 INC-009 는 조치하지 않음입니다. INC-003 과 INC-010 도 승인 대기입니다. INC-003 · INC-008 · INC-009 · INC-010 네 건이 왜 그렇게 나왔는지 단계 2 와 단계 4 의 줄을 근거로 적어 주세요. 또 이 네 건을 그대로 자동 처리했다면 누가 어떤 영향을 받았을지 적어 주세요.
  - 쓸 내용: ① INC-008 · INC-009 가 차단되지 않은 이유 ② INC-003 · INC-010 이 승인 대기인 이유 ③ 그대로 자동 처리했을 때의 영향
  - 답: ① INC-008(`192.0.2.41`)은 단계 2에 `여러 계정이 함께 쓰는 IP 라서 담당자 승인 필요`로 남았다. `ip_users.json`에서 `junho`와 `hana` 두 명이 함께 쓰는 공유 IP라 자동 차단하지 않고 승인 대기로 두었고, 단계 4에도 나온다. INC-009(`192.0.2.10`)는 `허용 목록 IP 라서 차단하지 않음`으로, 회사 취약점 점검 서버라 허용 목록에 있어서 조치하지 않았다(승인할 일도 아니라 단계 4에는 없다).
    ② INC-003과 INC-010은 대상이 VIP 계정 `gaeun`이라 화요일의 `decide_route`가 `승인 필요` 경로로 보냈고, `drill.py`의 4 · 5번에서 조치 없이 `승인 대기`가 됐다. 단계 4에 `INC-003 gaeun : VIP 계정이라 담당자 승인이 필요함`, `INC-010 gaeun : …` 두 줄로 나온다. INC-010은 인사 오류로 VIP가 퇴사자로 잘못 표시된 알림이다.
    ③ 그대로 자동 처리했다면 INC-008은 `junho`와 `hana`가 함께 접속하지 못하고, INC-009는 회사 점검 서버가 막혀 취약점 점검이 멈춘다. INC-010은 「퇴사한 계정」 규칙에 따라 계정 관리자인 `gaeun`이 잠기고 세션까지 끊겨 계정 관리 업무가 멈출 수 있었다(오전에 만든 조치 함수가 VIP를 한 번 더 막아 주지만, 담당자에게 넘어가지 않아 인사 오류가 드러나지 않는다).
