## 2교시 · 알림 한 건으로 티켓을 생성하고, 응답 기한(SLA)을 계산하며, 조치 확인에 실패한 건을 수동 확인 대상으로 표시하기

### 문제 2-1 · 알림 11건으로 티켓을 생성하고, 응답 기한(SLA)을 계산하며, 조치 확인에 실패한 건을 수동 확인 대상으로 표시하기

- (가) 실행한 출력 전체를 붙여 넣어 주세요. 그리고 단계 4 에 나온 직접 확인이 필요한 티켓 번호를 적어 주세요. 마지막으로 응답 기한 시각(담당자가 응답해야 하는 시각)이 가장 이른 티켓 번호를 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 단계 4 의 직접 확인이 필요한 티켓 번호 ③ 응답 기한 시각이 가장 이른 티켓 번호
  - 답: 단계 4의 직접 확인이 필요한 티켓은 TCK-7(INC-207, `203.0.113.250` 경로 스캔) 한 장이다. 응답 기한 시각이 가장 이른 티켓은 TCK-1(15분)이다.

- (나) 🔍 `INC-207` 은 상태가 `조치됨` 인데, 티켓의 후속 조치(`next_step`)는 「조치됨」용 문장이 아닙니다. `done` 의 문장을 근거로 그 사유를 적어 주세요. 그다음 이 표시가 없으면 담당자가 무엇을 놓칠 수 있는지 적어 주세요.
  - 쓸 내용: ① INC-207 의 `done` 문장 ② 다음 할 일이 「조치됨」용 문장이 아닌 이유 ③ 이 표시가 없을 때 놓칠 수 있는 일
  - 답: ① INC-207의 `done`은 `IP 차단: 차단되지 않음 → 차단되지 않음 (확인 실패)`이다.
    ② 상태는 `조치됨`이지만 조치 내역에 「확인 실패」가 들어 있어서, `has_failed_action`이 True를 리턴했다. 그래서 `make_ticket`이 「조치됨」용 문장 대신 `MANUAL_STEP`(조치가 확인되지 않았다. 담당자가 직접 계정이나 IP 상태를 보고 조치한다)으로 바꿨다. 실제로는 IP가 차단되지 않았기 때문이다.
    ③ 이 표시가 없으면 티켓에 「조치 결과가 맞는지 확인하고…」만 보여서, 담당자는 IP가 이미 차단됐다고 믿고 넘어갈 수 있다. 그러면 차단되지 않은 공격 IP `203.0.113.250`의 접속이 계속되는 것을 놓친다.

- (다) 🔍 TCK-1 의 응답 기한 시각은 15분이고 TCK-2 는 243분입니다. 두 티켓의 등급과 만든 시각을 근거로 응답 기한 시각을 계산하는 방법을 적어 주세요. 그다음 모든 티켓에 같은 응답 기한을 적용하면 어떤 문제가 생기는지 적어 주세요.
  - 쓸 내용: ① TCK-1 과 TCK-2 의 등급 · 만든 시각 · 기한 계산 ② 모든 티켓에 같은 기한을 쓸 때의 문제
  - 답: ① 응답 기한 시각 = 알림을 받은 시각(`minute`) + 등급별 응답 기한(`sla_minutes`)이다. TCK-1은 high라 기한 15분이고 0분에 만들어져 0 + 15 = 15분, TCK-2는 low라 기한 240분이고 3분에 만들어져 3 + 240 = 243분이다.
    ② 모두 240분으로 하면 퇴사자 계정 같은 긴급한 high 알림도 4시간 뒤에 확인해도 되는 것이 되어 대응이 늦어진다. 모두 15분으로 하면 급하지 않은 low 알림까지 15분 안에 봐야 해서 담당자가 감당하지 못하고, 정작 급한 건을 가려낼 수 없다. 심각도에 따라 처리 순서를 정할 수 없게 된다.
