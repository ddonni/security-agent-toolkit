- (가) 실행한 출력 전체를 붙여 넣고, 처리 뒤 티켓 수 · 담당자 알림 수 · `분류됨` 으로 남은 알림의 번호를 각각 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 처리 뒤 티켓 수 ③ 담당자 알림 수 ④ `분류됨` 으로 남은 건의 번호
  - 답: 처리 뒤 티켓은 1건, 담당자 알림은 1건이고, `분류됨`으로 남은 건은 INC-005이다.

INC-002 PB-002 티켓 생성 : 티켓 TCK-1 생성 (승인: kim.sec)

    ② `kim.sec`이 거절해서 상태가 `종료`가 되었다(단계 2 `거절 처리 (상태: 종료)`).

## 6교시 · 연결 오류가 나면 최대 3번 시도하고, 실패한 건을 목록으로 모으고, 오늘 만든 하루 흐름 전체 읽기

### 문제 6-1 · 연결 오류가 나면 최대 3번 시도하고, 실패한 건을 목록으로 모으기

- (가) 실행한 출력 전체를 붙여 넣고, 단계 3 에서 `일부 실패` · `승인 대기` · `오탐 종료`(오탐: 위험하지 않은데 위험하다고 잘못 알린 경우) 인 알림의 번호를 각각 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② `일부 실패` 인 알림 번호 ③ `승인 대기` 인 알림 번호 ④ `오탐 종료` 인 알림 번호
  - 답: 단계 3에서 `일부 실패`는 INC-001, `승인 대기`는 INC-002 · INC-003 · INC-005, `오탐 종료`는 INC-004이다.

```
--- 단계 1: 일시 장애 — 티켓 서비스가 2번 실패한 뒤 복구
티켓 TCK-1 생성 (시도 3회)
만든 티켓: 1 건
--- 단계 2: 서비스 중단 — 티켓 서비스가 계속 실패
실패: 연결 실패: 티켓 생성 서비스가 응답하지 않음 (3회 모두 실패)
만든 티켓: 0 건
--- 단계 3: 하루 흐름 — 티켓 서비스가 계속 실패하는 상황
INC-001 dami -> 일부 실패 (상태: 분류됨)
INC-002 seoyeon -> 승인 대기 (상태: 분류됨)
INC-003 gaeun -> 승인 대기 (상태: 분류됨)
INC-004 jiwoo -> 오탐 종료 (상태: 종료)
INC-005 198.51.100.90 -> 승인 대기 (상태: 분류됨)
--- 단계 4: 담당자 결정 처리
INC-002 seoyeon -> 실행 완료 (상태: 조치됨)
INC-003 gaeun -> 거절 처리 (상태: 종료)
INC-005 198.51.100.90 -> 권한 없음 (상태: 분류됨)
--- 단계 5: 하루가 끝난 뒤 모의 시스템 상태
잠긴 계정: ['dami']
차단한 IP: []
티켓: 1 건 · 담당자 알림: 1 건
--- 단계 6: 담당자 확인이 필요한 건
INC-001 티켓 생성 : 실패: 연결 실패: 티켓 생성 서비스가 응답하지 않음 (3회 모두 실패)
INC-005 승인 대기 : 플레이북 승인 값이 담당자 승인 필요
```

- (나) 🔍 단계 1 과 2 는 같은 `run_with_retry` 인데 결과가 다릅니다. 두 단계의 `fail_plan` 값을 근거로 이유를 적어 주세요. 그리고 최대 횟수가 없으면 서비스가 계속 멈춰 있을 때 어떤 문제가 생기는지도 적어 주세요.
  - 쓸 내용: ① 단계 1 과 2 의 `fail_plan` 값 ② 결과가 달라진 이유 ③ 최대 시도 횟수가 없을 때의 문제
  - 답: ① 단계 1의 `fail_plan`은 `{"INC-001|티켓 생성": 2}`, 단계 2는 `{"INC-001|티켓 생성": 99}`이다.
    ② 단계 1은 2번만 실패하도록 정해져 있어서 3번째 시도에서 성공했다(`티켓 TCK-1 생성 (시도 3회)`). 단계 2는 99번 실패하도록 정해져 있어 `MAX_TRIES` 3번이 모두 실패했다(`3회 모두 실패`, 만든 티켓 0건). 코드는 같아도 서비스가 잠깐 멈췄는지 계속 멈췄는지에 따라 결과가 달라진다.
    ③ 최대 횟수가 없으면 서비스가 계속 멈춰 있을 때 같은 요청을 끝없이 다시 보내서, 그 알림에서 대응 전체가 멈추고 뒤의 알림은 처리되지 않는다. 이미 멈춘 서비스에 요청이 계속 몰려 복구도 늦어지고, 실패했다는 기록도 남지 않아 담당자가 알 수 없다.

- (다) 🔍 단계 3 에서 INC-001 은 계정은 잠겼는데 상태가 `조치됨` 이 아닙니다. 그 이유를 적어 주세요. 또 단계 6 의 출력이 담당자에게 무엇을 알려 주는지 적어 주세요. 마지막으로, 같은 `state` 로 다시 처리해도 `dami` 가 두 번 잠기지 않는 이유를 오전 4교시에서 만든 장치와 연결해 적어 주세요.
  - 쓸 내용: ① INC-001 이 `조치됨` 이 아닌 이유 ② 단계 6 이 담당자에게 알려 주는 것 ③ 다시 실행해도 `dami` 가 두 번 잠기지 않는 이유
  - 답: ① INC-001은 계정 잠금은 성공했지만 티켓 생성이 3번 모두 실패했다. `run_playbook_with_retry`는 액션이 하나라도 「실패」로 끝나면 `failed`를 True로 바꾸고 `조치됨`으로 옮기지 않은 채 `일부 실패`를 리턴하므로 상태가 `분류됨`에 남았다.
    ② 단계 6은 담당자가 먼저 확인할 일을 알려 준다. `INC-001 티켓 생성 : 실패: …`는 INC-001의 티켓이 아직 만들어지지 않았다는 사실과 그 이유(티켓 서비스 응답 없음)를, `INC-005 승인 대기 : …`는 권한 있는 담당자의 승인을 아직 받지 못한 건이 남아 있다는 것을 알려 준다.
    ③ 오전 4교시에 만든 `safe_runner.py`의 `safe_run_action`이 실행 전에 `find_skip_reason`으로 확인해서, `dami`가 이미 `state["locked_users"]`에 있으면 잠그지 않고 「건너뜀: 이미 잠겨 있음」을 리턴하기 때문이다. 하루 흐름도 `flaky_run_action`이 이 함수를 불러 실행한다. 다만 티켓과 담당자 알림은 중복을 막지 않아, 같은 `state`로 다시 처리하면 한 번 더 만들어진다.
