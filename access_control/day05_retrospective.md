
# 3과목 총정리 (곽도현 · 2026-11-02(월))

## 상황 1 · 새 직원이 들어옴 (본보기)

- 원인: 데이터 문제입니다. hana 가 입사했는데 `users.json` 에 hana 가 아직 없습니다. 시스템은 사용자 파일에 없는 사람의 요청을 모두 「등록되지 않은 사용자」로 거부합니다.
- 고칠 파일: `config/users.json`
- 어떻게 고치나요: 새로 넣습니다. hana 를 `"hana": {"role": "sales", "employed": true}` 로 `users.json` 에 적습니다. `role` 은 hana 가 맡을 일에 맞는 역할로 정합니다.
- 고친 뒤 확인: hana 의 요청을 다시 판정해서 「등록되지 않은 사용자」가 사라지는지 봅니다.

## 상황 2 · 퇴사자 계정으로 요청이 계속 들어옴 (본보기)

- 원인: 데이터가 정리되지 않았습니다. dami 는 퇴사했는데 dami 의 항목이 `users.json` 에 그대로 남아 있어서 같은 시도가 계속 들어옵니다. `employed` 가 `false` 이면 요청은 거부되지만, 남은 항목 때문에 퇴사자 계정 점검에는 계속 걸립니다.
- 고칠 파일: `config/users.json`
- 어떻게 고치나요: dami 의 `"employed"` 가 `true` 로 남아 있다면 먼저 `false` 로 바꿉니다. 이미 `false` 이면 그대로 두고, dami 의 항목 전체를 `users.json` 에서 지웁니다.
- 고친 뒤 확인: 같은 요청이 「등록되지 않은 사용자」로 거부되고, 퇴사자 계정 점검이 통과로 바뀌는지 봅니다.
- 더 써 보고 싶은 것(선택): `check_permission` 이 퇴사 여부를 역할 확인보다 먼저 보는 이유는 무엇일까요?

## 상황 3 · 다른 팀 업무를 잠시 지원함

- 원인: 시스템 오류가 아닙니다. 지원 나간 직원의 역할에는 다른 팀 업무 권한이 없으니, 정책대로 거부된 것입니다. 다만 업무상 잠깐 필요한 권한이 반영되지 않은 상태입니다.
- 고칠 파일: config/exceptions.json
- 어떻게 고치나요: 역할은 바꾸지 않고 만료일이 있는 예외를 새로 넣습니다. 사용자, 필요한 권한, 사유, 승인자, 만료일(지원 종료일)을 적습니다.
- 고친 뒤 확인: 그 직원의 요청이 허용되는지 봅니다. 만료일이 지나면 다시 거부되고 만료 예외 점검에도 걸리는지 확인합니다.
- 더 써 보고 싶은 것(선택): 역할을 바꾸지 않는 이유가 있습니다. 역할을 바꾸면 지원이 끝난 뒤에도 권한이 남아서, 원래 업무에 필요 없는 권한이 계속 쌓입니다. 예외는 만료일이 있어서 자동으로 끝납니다

## 상황 4 · 새 권한이 필요함

- 원인: 권한을 달라는 요청을 처리하는 정해진 절차가 없습니다. junho 가 `SALES:CHANGE` 를 달라고 하는데 누가 승인하고 언제까지 처리할지 정해져 있지 않습니다. 절차가 없으면 담당자가 파일을 직접 고쳐 권한을 주게 되고, 누가 언제 왜 승인했는지 기록이 남지 않습니다.
- 고칠 파일: `req_create.py`(요청서) · `req_review.py`(승인) · `req_grant.py`(부여) · `req_sla.py`(처리 기한), 기한은 `config/sla.json`
- 어떻게 고치나요: 새로 넣습니다. `create_request` 로 요청서를 만들고, 요청자가 아닌 사람이 `approve_request` 로 승인하고, 승인된 요청서만 `grant_request` 로 부여합니다. 부여하면 예외 리스트에 새 예외가 추가됩니다. 오래 처리되지 않은 요청서는 `check_sla_breach` 로 찾아 담당자에게 알립니다.
- 고친 뒤 확인: 요청서의 `status` 가 `reviewing` → `approved` → `granted` 로 바뀌고 junho 의 `SALES:CHANGE` 요청이 예외로 허용되는지 봅니다. 본인이 승인하면 「본인 요청은 처리할 수 없음」이 나오는지도 봅니다.
- 더 써 보고 싶은 것(선택): 역할에 바로 넣지 않고 예외로 주는 이유가 있습니다. 실적 정정은 junho 한 명의 일시적인 일이라, 역할에 넣으면 같은 역할의 모든 사람이 쓰기 권한을 갖게 됩니다.

## 상황 5 · 안 쓰는 권한이 쌓임

- 원인: 한 번 준 권한이 쓰이지 않는데도 남아 있습니다. 점검(`find_stale` · `find_unused`)은 마지막 사용이 90일을 넘었거나 사용 이력이 없는 권한을 회수 후보로 뽑습니다. junho 의 `SALES:QUERY`(91일째)는 정말 필요 없는 권한이지만, seoyeon 의 `SALES:CHANGE`(120일째, 6월 · 12월 결산 때만 씀)와 gaeun 의 `ACCOUNT:CHANGE`(계정 사고 때만 씀)는 드물게 쓸 뿐 필요한 권한입니다.
- 고칠 파일: `config/exclude_list.json` (점검 코드는 `review_rules.py` · `review_unused.py`, 사용 기록은 `config/access_log.json`)
- 어떻게 고치나요: 정말 필요 없는 권한은 회수 대상으로 넘깁니다(실제 회수는 상황 6). 드물게 쓰는 권한은 `exclude_list.json` 에 사용자 · 권한 · 제외 이유를 새로 넣습니다. 퇴사한 dami 의 권한은 제외 리스트에 있어도 제외하지 않습니다(`can_exclude`).
- 고친 뒤 확인: junho 의 `SALES:QUERY` 는 회수 대상에, seoyeon · gaeun 의 권한은 회수 제외에 나오는지 봅니다. 정확히 90일째인 junho 의 `SETTLE:QUERY` 는 후보가 아닌지도 봅니다(기준이 「90일을 넘으면」).
- 더 써 보고 싶은 것(선택): 제외할 때 이유를 꼭 적는 이유가 있습니다. 이유가 없으면 반년 뒤 점검 때 왜 제외했는지 아무도 모르고, 제외 리스트가 회수를 피하는 구멍이 됩니다.

## 상황 6 · 민감한 권한을 회수해야 함

- 원인: 회수 대상에 쓰기 권한이 섞여 있고, 퇴사자의 역할을 비우면 권한 여러 개가 한꺼번에 사라집니다. 잘못 회수하면 업무가 멈추고 되돌리기 어렵습니다.
- 고칠 파일: 받은 방식에 따라 `config/exceptions.json`(예외 삭제) · `config/users.json`(퇴사자의 role 비우기) · `config/roles.json`(재직자 역할에서 권한 빼기). 절차는 `revoke_plan.py` → `revoke_approve.py` → `revoke.py`, 이력은 `revocation_log.json`
- 어떻게 고치나요: 먼저 계획(dry-run)으로 무엇이 몇 건 사라지는지 봅니다. 민감한 권한(`sensitive.json`)이거나 영향이 2건 이상이면 보안 책임자의 승인을 받고, 승인이 없거나 거절되면 「승인 대기」로 두고 실행하지 않습니다. 실행한 것과 대기한 것 모두 이력에 남깁니다.
- 고친 뒤 확인: 회수 전후 판정을 비교합니다(junho 의 `SALES:QUERY` 는 허용 → 거부). 판정이 「거부 → 거부」로 그대로인 건 데이터를 직접 `print` 해서 정말 지워졌는지 봅니다. 이력에 실행 7 · 대기 1 이 남는지 봅니다.
- 더 써 보고 싶은 것(선택): 이미 거부되던 권한도 회수하는 이유가 있습니다. 거부와 회수는 다릅니다. 데이터에 권한이 남아 있으면 재직 표시 실수나 만료 시각 수정 한 번에 되살아납니다.

## 상황 7 · 새벽 외부 접속, 그리고 정상 직원이 계속 거부됨

- 원인: 둘 다 규칙 문제입니다. 새벽 외부 요청이 허용된 건 `conditions.json` 에 그 권한의 시간 · 접속 위치 조건이 없어서입니다(조건이 없는 권한은 역할 판정 그대로 허용). gaeun 이 VPN 으로 거부된 건 `ACCOUNT:CHANGE` 의 접속 위치가 `["office"]` 뿐이라 실제 일하는 방식과 맞지 않아서입니다.
- 고칠 파일: `config/conditions.json` (판정 코드는 `conditional.py` 의 `evaluate_conditional`)
- 어떻게 고치나요: 빠진 권한은 조건을 새로 넣습니다. 예: `{"permission": "SALES:CHANGE", "hours": [9, 18], "networks": ["office", "vpn"]}`. gaeun 은 확인한 뒤 `ACCOUNT:CHANGE` 의 접속 위치를 `["office", "vpn"]` 으로 바꿉니다. `external` 은 넣지 않습니다.
- 고친 뒤 확인: 밖에서 22시에 보낸 요청이 「업무 시간 밖」으로 거부되고, gaeun 의 VPN 요청은 허용되는지 봅니다. 규칙을 풀었으니 다른 요청이 같이 허용되지 않는지도 봅니다.
- 더 써 보고 싶은 것(선택): 오탐이 귀찮다고 규칙 전체를 풀면 진짜 공격도 함께 통과합니다. 규칙은 유지하고 허용 범위를 좁게 넓히는 쪽이 안전합니다. 시간대 `[9, 18]` 은 18시 정각을 포함하지 않는다는 점도 기억합니다.

## 상황 8 · 매주 어긋남을 확인해야 함

- 원인: 사람이 로그를 눈으로 세면 오래 걸리고 기준이 사람마다 다릅니다. 데이터는 입사 · 퇴사 · 부서 이동 · 예외 만료로 계속 어긋나기 때문에 한 번 고친다고 끝나지 않습니다.
- 고칠 파일: 새로 만드는 `checklist.py`(점검) · `log_summary.py`(집계) · `weekly_report.py`(보고서). 경고 기준은 `config/alert.json`
- 어떻게 고치나요: 점검 세 가지, 로그 집계, 주간 보고서를 코드로 만들어 매주 같은 기준으로 돌립니다. 경고가 매주 뜨거나 위험을 놓치면 `alert.json` 의 `deny_rate_limit` 를 바꾸고 바꾼 이유를 기록합니다.
- 고친 뒤 확인: 보고서 4절에 조치가 필요한 것이 나오는지 봅니다. 기준을 30% 에서 50% 로 올리면 같은 로그가 「경고 없음」이 되는데, 거부 수는 그대로이므로 안전해진 게 아니라 기준이 바뀐 것입니다. 요청이 0건인 주는 거부율 0% 로 나오니 전체 요청 수부터 봅니다.
- 더 써 보고 싶은 것(선택): 점검이 자동으로 고치지 않는 이유가 있습니다. 점검 코드는 불일치를 알려 줄 뿐, 그게 정당한 겸직인지 데이터 오류인지는 모릅니다. 탐지는 자동으로, 판단은 사람이 합니다. 이 주간 점검은 cron 이나 GitHub Actions 스케줄로 자동 실행할 수 있습니다.
