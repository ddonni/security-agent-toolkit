## 2교시 · 서버가 거절한 요청 중 반복된 것을 찾고 이유로 순서 정하기

### 문제 2-1 · 서버가 거절한 요청 중 반복된 것을 찾고 이유로 순서 정하기

- (가) 실행한 출력 전체를 붙여 넣고, 서버 실패 수와 먼저 확인할 이벤트 수, 1순위 사용자를 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 서버 실패 수 ③ 먼저 확인할 이벤트 수 ④ 1순위 사용자
  - 답: 서버 실패는 9개, 먼저 확인할 이벤트는 7개, 1순위 사용자는 dami이다.

```
--- 단계 1: 판정 서버의 실패 이벤트 9 개
--- 단계 2: 먼저 확인할 실패 이벤트 7 개
--- 단계 3: 우선순위
1 퇴사한 계정 dami SALES:QUERY 2026-11-02 11:02:00
1 퇴사한 계정 dami SALES:QUERY 2026-11-02 11:03:00
1 퇴사한 계정 dami SALES:CHANGE 2026-11-02 11:05:00
1 퇴사한 계정 dami SALES:QUERY 2026-11-02 11:08:00
3 규칙은 허용인데 서버가 거절 gaeun ACCOUNT:CHANGE 2026-11-02 10:05:00
3 규칙은 허용인데 서버가 거절 gaeun ACCOUNT:CHANGE 2026-11-02 10:09:00
3 규칙은 허용인데 서버가 거절 gaeun ACCOUNT:CHANGE 2026-11-02 10:14:00
```

- (나) 🔍 ① dami 의 실패 4개는 3과목(접근통제) 규칙으로 어떤 이유로 판정됐고, 왜 1순위일까요? ② gaeun 의 실패 3개는 규칙으로는 「허용」인데 서버가 거절했습니다. 공격이라고 확정할 수 있는지 적고, 먼저 무엇을 확인해야 하는지 적어 주세요.
  - 쓸 내용: ① dami 의 판정 이유와 1순위인 까닭 ② 공격이라고 확정할 수 있는지와 먼저 확인할 것
  - 답: ① dami의 실패 4건(11:02~11:08)은 `check_permission`에서 모두 「퇴사한 계정」으로 판정됐다. users.json에서 dami의 `employed`가 false이기 때문이다. 퇴사했는데 계정이 남아 있고 그 계정으로 서버 요청이 4번 들어왔으므로, 계정이 정리되지 않았다는 뜻이다. 다른 거절과 달리 계정 정리라는 조치가 바로 필요하므로 1순위이다.
    ② 공격이라고 확정할 수 없다. gaeun의 역할 `account_admin`에는 `ACCOUNT:CHANGE` 권한이 있어 규칙상 허용되는 요청이고, 같은 요청이 10:05~10:14에 3번 거절됐다는 사실만으로는 공격의 근거가 부족하다. 규칙과 서버의 판단이 어긋난 것이므로, 먼저 서버가 이 요청을 거절한 이유(서버 설정이나 다른 조건)를 확인해야 한다.

- (다) 🔍 seoyeon 의 서버 실패 2건(11:40 `SETTLE:QUERY` · 18:20 `SALES:CHANGE`)은 먼저 확인할 이벤트에 들어가지 않았습니다. 들어가지 않은 이유를 오늘 규칙(실패 3번 이상)으로 설명하고, 이 규칙 때문에 놓칠 수 있는 경우를 한 가지 적어 주세요.
  - 쓸 내용: ① 먼저 확인할 이벤트에 들어가지 않은 이유 ② 이 규칙이 놓칠 수 있는 경우 한 가지
  - 답: ① seoyeon의 서버 실패는 11:40과 18:20의 2번뿐이라 기준인 `REPEAT_LIMIT` 3번에 못 미쳐 먼저 확인할 이벤트에 들어가지 않았다.
    ② 이 규칙은 횟수만 보기 때문에 실패 횟수가 적으면 중요한 요청도 놓칠 수 있다. 예를 들어 11:40 `SETTLE:QUERY`는 seoyeon의 역할 `sales`에 없는 권한이라 「권한 없음」에 해당하지만, 실패가 2번뿐이라 먼저 확인할 대상에서 빠졌다. 정산처럼 중요한 자원에 권한 없이 접근을 시도해도 3번 미만이면 놓치게 된다.

## 3교시 · SaaS 로그에서 이상 사용 세 가지 찾기

### 문제 3-1 · SaaS 로그에서 이상 사용 세 가지 찾기

- (가) 실행한 출력 전체를 붙여 넣고, 규칙마다 해당한 사용자를 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 업무 시간 밖 로그인 사용자 ③ 평소와 다른 IP 사용자 ④ 대량 다운로드 사용자
  - 답: 업무 시간 밖 로그인은 jiwoo, 평소와 다른 IP는 jiwoo · seoyeon, 대량 다운로드는 seoyeon이다.

```
--- 단계 1: 업무 시간 밖 로그인 1 건
                  time source   user            ip action result
0  2026-11-02 02:14:08   saas  jiwoo  203.0.113.80  login     실패
--- 단계 2: 평소와 다른 IP 로 로그인한 사용자 ['jiwoo', 'seoyeon']
--- 단계 3: 파일을 5번 이상 내려받은 사용자 ['seoyeon']
```

- (나) 🔍 jiwoo 는 업무 시간 밖(02:14)과 평소와 다른 IP 두 규칙에 해당하지만 그 로그인은 실패였습니다. 이 기록만으로 계정 도용을 확정할 수 있나요? 그렇게 판단한 이유와, 샘플 로그에서 더 찾아볼 수 있는 것을 한 가지 적어 주세요.
  - 쓸 내용: ① 도용이라고 확정할 수 있는지 없는지 ② 더 확인할 정보 한 가지
  - 답: ① 확정할 수 없다. jiwoo의 02:14 로그인(203.0.113.80)은 실패였고, 같은 날 16:02에는 평소 IP(198.51.100.52)로 로그인에 성공했다. 다른 IP에서 실패한 시도가 한 번 있었을 뿐이라 계정이 실제로 도용됐다는 근거가 부족하다.
    ② 같은 IP 203.0.113.80의 다른 활동을 더 찾아본다. 샘플 로그에서 이 IP는 17:38에 seoyeon 계정으로 로그인에 성공했고, 이어서 17:40~17:42에 파일을 5번 내려받았으므로 함께 확인할 필요가 있다.

- (다) 🔍 gaeun 은 평소 IP 기록이 없어 「평소와 다른 IP」 규칙에서 제외됩니다. 제외하지 않으면 어떤 일이 생기고, 제외하면 어떤 위험이 남나요?
  - 쓸 내용: ① 제외하지 않을 때 생기는 일 ② 제외했을 때 남는 위험
  - 답: ① 제외하지 않으면 비교할 평소 IP가 없는데도 gaeun의 정상 로그인(198.51.100.77)이 「평소와 다른 IP」로 탐지되어 오탐 알림이 늘어난다.
    ② 제외하면 다른 사람이 gaeun 계정을 쓰고 있어도 이 규칙으로는 찾지 못하는 위험이 남는다. 그래서 평소 기록을 먼저 수집한 뒤에 규칙을 적용해야 한다.

## 4교시 · 웹 실패 로그에서 경로를 스캔한 IP 찾기

### 문제 4-1 · 웹 실패 로그에서 경로를 스캔한 IP 찾기

- (가) 실행한 출력 전체를 붙여 넣고, 스캔으로 본 IP 와 이유를 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 스캔으로 본 IP ③ 이유
  - 답: 스캔으로 본 IP는 198.51.100.90 하나이고, 이유는 「스캐너 경로를 3번 요청」이다(`/.env` · `/wp-login.php` · `/phpmyadmin`).

```
--- 단계 1: 웹 서버의 실패 이벤트 13 개
--- 단계 2: 스캐너 경로를 요청한 IP 와 횟수
ip
198.51.100.90    3
Name: count, dtype: int64
--- 단계 3: 스캔으로 본 IP 와 이유
{'ip': '198.51.100.90', 'reason': '스캐너 경로를 3번 요청'}
--- 단계 4: 스캐너 경로가 없어 제외한 IP
203.0.113.50
198.51.100.21
198.51.100.34
198.51.100.77
```

`advanced_detection.py` 출력

```
판정 서버: 먼저 확인할 실패 이벤트 7 개
SaaS: 업무 시간 밖 ['jiwoo'] · 평소와 다른 IP ['jiwoo', 'seoyeon'] · 대량 다운로드 ['seoyeon']
웹 서버: 스캔으로 본 IP ['198.51.100.90']
```

- (나) 🔍 203.0.113.50 은 실패한 요청이 7번 있지만 스캔에서 제외됐습니다. 제외된 이유와, 제외하지 않으면 담당자에게 어떤 일이 생기는지 적어 주세요.
  - 쓸 내용: ① 제외된 이유 ② 제외하지 않을 때 생기는 일
  - 답: ① 203.0.113.50의 실패 7번은 `POST /login` 5번, `GET /admin`, `GET /admin/users`로, `SCANNER_PATTERN`의 경로가 하나도 없어서 제외됐다.
    ② 제외하지 않으면 경로 스캔 알림에 로그인 실패와 관리자 화면 접근 실패가 섞여, 담당자가 경로 스캔과 로그인 실패를 구분하기 어려워진다. 이 IP는 로그인 규칙에서 따로 다룰 대상이다.

- (다) 🔍 198.51.100.21 의 `GET /board/99` 실패 1건은 이 규칙에서 어떤 조건 때문에 제외되나요? 그리고 해킹 도구가 `SCANNER_PATTERN` 에 없는 경로(예: `/backup.zip`)를 요청하면 이 규칙이 탐지하지 못한다는 점을 설명해 주세요.
  - 쓸 내용: ① 한 번의 실패가 제외되는 과정 ② 목록에 없는 경로를 요청하면 탐지하지 못한다는 점
  - 답: ① `GET /board/99`는 `SCANNER_PATTERN`의 세 경로(`/.env` · `/wp-login` · `/phpmyadmin`) 중 어느 것도 들어 있지 않아 `is_scanner`가 False가 되고, 그래서 `scanner_rows`에 들어가지 않아 제외된다.
    ② 이 규칙은 정해 둔 경로 목록만 확인한다. 해킹 도구가 `/backup.zip`처럼 목록에 없는 경로를 요청하면 `str.contains`가 False를 돌려주므로 탐지하지 못한다. 그래서 경로 목록을 새 위협에 맞춰 계속 갱신해야 한다.
