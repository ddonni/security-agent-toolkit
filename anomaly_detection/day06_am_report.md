- (가) 실행한 출력 전체를 붙여 넣고, 요약한 대상 수와 `(요약 실패 …)` 가 나온 대상 수를 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 요약한 대상 수 ③ `(요약 실패 …)` 가 나온 대상 수
  - 답: 점수 기록은 5건이고, 요약한 대상은 3명(dami · seoyeon · gaeun)이다. `(요약 실패 …)`가 나온 대상은 0명이다.


- (나) 🔍 단계 3 의 지시문이 AI 에게 하지 말라고 한 것 두 가지를 찾고, 각각 하면 왜 위험한지 적어 주세요.

  - 쓸 내용: ① 고른 요약의 대상 ② 표에 없는 내용이 있는지 ③ 있으면 그 문장과 지시문을 고칠 방법, 없으면 탐지된 규칙이 모두 들어갔는지
  - 답: ① seoyeon의 요약을 골랐다.

  - 답: ① AI는 바깥 서비스라서 한도 초과(429)나 네트워크 문제로 언제든 실패할 수 있다. 요약 하나가 실패했다고 파이프라인이 멈추면 점수와 등급이 담긴 보고서까지 만들어지지 않아 담당자가 아무것도 볼 수 없다. 요약은 보조 설명이고 핵심은 점수와 등급이므로, 실패한 요약만 `FAIL_TEXT`로 채우고 나머지 단계를 이어 간다.

## 4교시 · 4과목 총정리: 상황마다 원인과 고치는 방법 정리하기

### 문제 4-1 · 상황 8개의 원인과 고치는 방법을 내 말로 정리하기

**상황 정리** — 상황 1 · 2 · 3 · 4 · 7 · 8 중 4개 이상 씁니다. 상황 5 · 6 은 본보기입니다.

#### 상황 1 · 설정 파일 주소를 연달아 요청했는데 「의심」이 아니라 「오류」로 분류됨
- 원인: 규칙 문제입니다. `log_classify.py`의 `is_suspicious`는 요청 하나의 상태 코드가 401 · 403이거나 경로에 `/admin`이 있을 때만 「의심」으로 가립니다. 198.51.100.90의 세 요청은 모두 404이고 `/admin`이 없어서 의심 조건에 맞지 않고, 400 이상인 `is_error`에만 맞아 「오류」가 됩니다. 한 줄씩 보면 흔한 404이지만, 설정 파일 · 관리 화면 주소를 1초 간격으로 연달아 요청한 것은 스캔입니다. 이 규칙은 경로 이름과 반복을 보지 않아서 미탐이 생깁니다.
- 고칠 파일: `log_classify.py` (`is_suspicious`)
- 어떻게 고치나요:
  - 케이스 A: 값을 바꿉니다. `is_suspicious`에 「경로에 `/.env` · `/wp-login` · `/phpmyadmin` 중 하나가 들어 있다」는 조건을 더해 `or`로 잇습니다.
  - 케이스 B: 경로 목록만 늘리면 목록에 없는 주소는 또 놓치므로, 같은 IP가 없는 주소를 연달아 요청한 횟수를 세는 규칙을 새로 넣습니다. 11/5 오전 `malicious_detection.py`의 `find_scan_ips`가 이 방식입니다.
- 고친 뒤 확인: 같은 로그를 다시 분류해 198.51.100.90의 세 줄이 「의심」에 나오는지 봅니다. 분류별 개수가 정상 15 · 오류 5 · 의심 8에서 정상 15 · 오류 2 · 의심 11로 바뀌어야 합니다.
- 담당자가 가장 먼저 할 일(선택): 198.51.100.90이 같은 시간대에 다른 경로도 요청했는지, 그중 성공(200)한 요청이 있는지 접속 기록에서 확인합니다.

#### 상황 2 · 로그 30줄이 이벤트 28개가 됨
- 원인: 데이터 문제입니다. 원본 로그 30줄 중 2줄은 중간에 잘렸거나 `-` 하나뿐이라 큰따옴표가 두 개보다 적습니다. `normalize_web`은 이런 깨진 줄을 읽지 않고 `None`을 리턴하므로 이벤트가 28개가 됩니다. 줄이 사라진 것이 아니라 읽기에 실패한 것입니다.
- 고칠 파일: 고칠 코드는 없습니다. 정규화 코드(`normalize_web.py`)는 의도대로 깨진 줄을 걸렀고, 문제는 원본 로그의 두 줄입니다.
- 어떻게 고치나요:
  - 케이스 A: 코드는 그대로 두고, 읽기 성공 28 + 읽기 실패 2 = 전체 30이 맞는지 계산해 보고서에 적습니다.
  - 케이스 B: 로그를 쓰는 서버에서 줄이 끊기는 원인을 찾아 고칩니다(이 수업에서는 서버 설정을 바꾸지 않았습니다).
- 고친 뒤 확인: 정규화한 이벤트 수와 읽기 실패 줄 수를 더해 원본 줄 수 30과 같은지 봅니다. 11/3 실행 파일 단계 1의 `읽기 실패 2 줄`과 맞으면 사라진 줄 없이 모두 설명됩니다.
- 담당자가 가장 먼저 할 일(선택): 읽지 못한 2줄의 원문을 원본 로그에서 찾아, 서버가 쓰는 도중 끊긴 것인지 누가 고친 흔적인지 확인합니다.

#### 상황 3 · 웹 서버 로그에서 사용자를 알 수 있는 요청이 1개뿐
- 원인: 데이터 문제입니다. 웹 서버 로그에는 사용자 이름이 없고 IP만 있어서 이벤트의 `user`가 `None`입니다. `make_ip_user_map`은 SaaS에서 로그인에 성공한 IP로만 사용자를 찾는데, 웹 실패 요청 13개 중 그런 IP는 198.51.100.77(gaeun)의 `/admin` 1개뿐입니다. 203.0.113.50은 SaaS · 판정 서버 로그에 기록이 없어 누구인지 알 수 없습니다.
- 고칠 파일: 케이스 A는 웹 서버의 로그 설정, 케이스 B는 `risk_scores.py`
- 어떻게 고치나요:
  - 케이스 A: 새로 넣습니다. 웹 서버가 로그인한 사용자 이름도 로그 한 줄에 남기도록 설정을 바꿉니다(이 수업에서는 바꾸지 않았습니다).
  - 케이스 B: 사용자를 모르는 요청은 사용자 대신 IP를 대상(`entity`)으로 점수를 매깁니다. 경로 스캔 198.51.100.90을 IP로 점수 매긴 것과 같은 방식입니다.
- 고친 뒤 확인: 케이스 A는 11/5 5교시 실행 파일 단계 1의 「IP 로 사용자를 알 수 있는 웹 실패 이벤트」가 1개보다 늘었는지 봅니다. 케이스 B는 점수 파일의 `entity`에 203.0.113.50 같은 IP가 나오는지 봅니다.
- 담당자가 가장 먼저 할 일(선택): 203.0.113.50이 09:12:18에 로그인에 성공한 계정이 무엇인지 웹 서버 쪽 기록에서 찾습니다.

#### 상황 4 · 두 로그에 나오는 seoyeon 이 연결되지 않음
- 원인: 규칙 문제입니다. `find_chains`는 한 사용자의 하루 첫 이벤트부터 마지막 이벤트까지의 시간(`span`)이 `WINDOW_MINUTES`(60분) 이내여야 연결합니다. seoyeon의 이벤트는 09:05부터 18:20까지 흩어져 있어 `span`이 555분이라 연결되지 않습니다. 17:38 다른 IP 로그인부터 18:20 서버 거절까지는 42분 안에 모여 있는데, 하루 전체로 계산해서 이 흐름을 놓칩니다. gaeun은 3종류가 41분 안이라 연결됐습니다.
- 고칠 파일: `correlation.py` (`find_chains`, `WINDOW_MINUTES`)
- 어떻게 고치나요:
  - 케이스 A: 값을 바꿉니다. `WINDOW_MINUTES`를 600으로 올리면 seoyeon이 `서로 다른 로그 2종류 · 555분 안`으로 연결됩니다. 다만 하루 전체가 한 사건이 되어 「짧은 시간 안에 모였다」는 뜻이 약해지고 오탐이 늘 수 있습니다.
  - 케이스 B: 계산 방식을 바꿉니다. 첫 이벤트와 마지막 이벤트의 차이 대신, 이웃한 이벤트 사이가 60분 이내로 이어지는 이벤트끼리만 한 사건으로 묶습니다. 그러면 17:38 ~ 18:20 묶음이 하나의 사건이 됩니다.
- 고친 뒤 확인: 11/5 `day04_5-1_run.py`를 다시 실행해 단계 3에 seoyeon이 나오는지, 단계 4에서 사라졌는지, 이유에 적힌 분이 어떻게 바뀌었는지 봅니다.
- 담당자가 가장 먼저 할 일(선택): seoyeon의 17:38 로그인(203.0.113.80)부터 18:20 서버 거절까지를 시간순으로 읽고, 다운로드한 파일 목록을 확인합니다.

#### 상황 5 · 협력사 사무실에서 접속한 정상 접속에 알림이 남 (본보기)
- 원인: 규칙 문제입니다. `SaaS 평소와 다른 IP` 규칙은 지난 접속 기록에 없는 IP 이면 모두 알림을 냅니다. 협력사 사무실 IP 203.0.113.80 에서 jiwoo(A4)와 seoyeon(A5)이 출장 · 외근 중에 접속했는데, 조사해 보니 모두 정상 접속이었습니다.
- 고칠 파일: `tuning.py` (`TRUSTED_IPS` 와 `apply_exception`)
- 어떻게 고치나요: 새로 넣고 뺍니다. 믿는 IP 리스트에 `203.0.113.80` 한 개를 넣고, `SaaS 평소와 다른 IP` 규칙의 알림 가운데 그 IP 에서 온 것만 알림 표에서 뺍니다. 다른 규칙의 알림(A3 · A6)은 같은 IP 여도 빼지 않습니다.
- 고친 뒤 확인: 오탐이 4개에서 2개로 줄었는지 보고, 빠진 알림 가운데 진짜 문제(`real` 이 `True`)가 0개인지 봅니다.

#### 상황 6 · 로그인 규칙이 낸 알림이 평가에서 빠짐 (본보기)
- 원인: 데이터 문제입니다. 로그인 규칙이 낸 알림 A8 은 `login_alerts.json` 에 따로 저장돼 있고, 첫 평가에 쓴 `review_alerts.json` 의 알림 7개에는 들어 있지 않습니다. 평가는 알림 7개만 보고 「알림이 난 진짜 문제」를 세므로, A8 이 가리키는 P4 가 미탐으로 셉니다. 규칙은 알림을 이미 냈지만 평가에 들어가지 못했습니다.
- 고칠 파일: `final_check.py` (`merge_alerts`)

- 고친 뒤 확인: 미탐이 2개(P4 · P5)에서 1개(P5)로 줄고 오탐은 2개 그대로인지 봅니다.

#### 상황 7 · 정산 조회 시도에는 알림이 나지 않음
- 원인: 규칙 문제입니다(그 일을 잡는 규칙이 없습니다). `pick_suspicious`는 한 사용자의 서버 실패가 `REPEAT_LIMIT`(3번) 이상일 때만 먼저 확인합니다. seoyeon의 서버 실패는 11:40 `SETTLE:QUERY`와 18:20 `SALES:CHANGE` 2번뿐이라 기준에 못 미쳐 P5가 미탐이 됩니다. 횟수만 보는 규칙은 중요한 권한을 한 번 건드린 일을 놓칩니다.
- 고칠 파일: `access_detection.py`
- 어떻게 고치나요: 새로 넣습니다. 중요한 권한 목록(예: `SENSITIVE_ACTIONS = ["SETTLE:QUERY"]`)을 정하고, 서버 실패 이벤트의 행동이 그 목록에 있으면 횟수와 상관없이 확인 대상에 넣는 함수를 `pick_suspicious` 옆에 더합니다. `REPEAT_LIMIT`를 1로 낮추는 방법도 있지만, 그러면 모든 실패에 알림이 나서 오탐이 크게 늘어납니다.
- 고친 뒤 확인: 같은 이벤트로 다시 실행해 seoyeon의 11:40 `SETTLE:QUERY`가 확인 대상에 나오는지 보고, 11/6 오전처럼 오탐과 미탐을 다시 세어 미탐이 1개(P5)에서 0개로 줄었는지, 오탐이 얼마나 늘었는지 봅니다.
- 담당자가 가장 먼저 할 일(선택): seoyeon에게 11:40 정산 조회가 업무상 필요한 요청이었는지 확인하고, 필요했다면 권한 요청 절차를 안내합니다.

#### 상황 8 · 서버가 같은 네트워크에 열려 있고, 지우면 접속 기록도 사라짐
- 원인: 운영 설정 문제입니다(두 가지).
  - 접속 범위: 5교시 `compose.yaml`의 `web2` 포트가 `"8081:80"`처럼 주소 없이 적혀 있어서 같은 네트워크의 다른 PC도 접속할 수 있습니다. `docker compose ps`의 PORTS에 `0.0.0.0:8081->80/tcp`로 나옵니다.
  - 접속 기록: 서버 안 로그 폴더를 내 폴더에 연결(`volumes`)하지 않아서, `down`으로 서버를 지우면 서버 안에 쌓인 접속 기록도 함께 사라집니다.
- 고칠 파일: `compose.secure.yaml` (`ports`, `volumes`)
- 어떻게 고치나요:
  - 케이스 A(접속 범위): 값을 바꿉니다. `"8081:80"`을 `"127.0.0.1:8081:80"`으로 바꿔 내 PC에서만 접속되게 합니다. 모두에게 열어 둘 `web1`은 그대로 둡니다.
  - 케이스 B(접속 기록): 새로 넣습니다. 서버 설정에 `volumes:` 아래 `- ./logs:/var/log/nginx`를 더해 접속 기록을 내 `logs` 폴더에 남깁니다.
- 고친 뒤 확인: 케이스 A는 `docker compose -f compose.secure.yaml ps`의 PORTS가 `127.0.0.1:8081->80/tcp`로 바뀌었는지 봅니다(11/6 내 출력에서 확인함). 케이스 B는 `down` 뒤에도 `ls logs`에 `access.log`가 남아 있는지 봅니다(11/6에 `access.log` · `error.log` · `web_404.log`가 남음).
- 담당자가 가장 먼저 할 일(선택): `logs/access.log`에 내 PC가 아닌 IP의 요청이 있는지, 스캐너 경로(`/.env` 등) 요청이 있는지 확인합니다.
