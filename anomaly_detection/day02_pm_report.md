## 5교시 · 정규화된 이벤트를 표로 읽고 실패만 골라 세기

### 문제 5-1 · 정규화된 이벤트 표를 읽어 실패한 이벤트를 소스별로 세기

- (가) 실행한 출력 전체를 붙여 넣고, 표의 행 수와 열 수, 성공과 실패 개수, 실패한 이벤트의 소스별 개수를 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 행 수 · 열 수와 성공 · 실패 개수 ③ 소스별 실패 개수
  - 답:

```
--- 단계 1: 표 크기(행 수, 열 수)와 처음 3개 시각
(57, 7)
2026-11-02 02:14:08
2026-11-02 09:01:05
2026-11-02 09:01:06
--- 단계 2: 성공 · 실패별 개수
result
성공    34
실패    23
Name: count, dtype: int64
--- 단계 3: 실패한 이벤트 23 개의 소스별 개수
source
web       13
server     9
saas       1
Name: count, dtype: int64
--- 단계 4: 전체 이벤트의 소스별 개수
source
web       28
server    15
saas      14
Name: count, dtype: int64
```

  - ② 표 57행 · 7열, 성공 34 · 실패 23
  - ③ 실패 소스별: web 13 · server 9 · saas 1

- (나) 🔍 실패 개수만 보면 web 이 가장 많습니다. 그렇다면 web 이 가장 문제가 큰 소스라고 말할 수 있을까요? 단계 4의 전체 이벤트 수와 함께 보고 이유를 적어 주세요.
  - 쓸 내용: ① 말할 수 있는지 없는지 ② 소스마다 전체 이벤트 수가 다르다는 것을 근거로 한 이유
  - 답: ① 말할 수 있는지 없는지
  - 말할 수 없습니다. 실패 개수는 web 이 13개로 가장 많지만, web 은 전체 이벤트 자체가 가장 많습니다.
  - ② 이유
  - 소스별 전체 이벤트 수(단계 4)는 web 28 · server 15 · saas 14 로 다릅니다. 이벤트가 많은 소스는 실패 개수도 많아지기 쉬워서, 개수만 비교하면 공평하지 않습니다.
  - 전체 대비 실패 비율로 보면 순서가 바뀝니다.
  - server: 9 ÷ 15 = 60%
  - web: 13 ÷ 28 ≈ 46%
  - saas: 1 ÷ 14 ≈ 7%
  - 비율로는 server 가 가장 높습니다. 3과목 거부율처럼 개수가 아니라 비율로 비교해야 합니다.
  - 덧붙여, web 의 「실패」는 상태 코드 400 이상을 모두 센 것입니다. 그래서 /board/99 404 나 /report 500 같은 평범한 오류도 섞여 있습니다. 실패가 곧 공격은 아닙니다.
- (다) 🔍 web 이벤트에는 `user` 가 비어 있습니다. 사용자 이름으로 실패를 세려 할 때 web 의 실패 13개는 어떻게 될지 예상하고, 사용자 대신 어떤 열을 보면 같은 대상이 반복했는지 알 수 있을지 이유와 함께 적어 주세요.

  - 쓸 내용: ① 사용자 이름으로 셀 때 web 실패 13개가 어떻게 될지 ② 대신 볼 열과 그 이유
  - 답: ① 사용자 이름으로 셀 때 web 실패 13개가 어떻게 될지
  - web 이벤트는 user 가 None(판다스에서는 빈 값)이라 사용자별로 세면 13개가 통째로 빠집니다. value_counts() 는 기본적으로 빈 값을 세지 않습니다. 그래서 사용자별 실패 횟수에는 server · saas 실패만 나오고, 무차별 대입처럼 web 에서 일어난 반복 실패는 보이지 않습니다.
  - ② 대신 볼 열과 그 이유
  - ip 열을 봅니다. web 로그에는 사용자 이름이 없는 대신 접속 주소가 있어서, 같은 주소가 반복했는지 알 수 있습니다. web 실패 13개를 ip 로 세면 이렇습니다.
  - 203.0.113.50: 7개 (로그인 401 ×5, /admin 403 ×2) → 같은 대상의 로그인 반복 실패와 관리자 페이지 접근
  - 198.51.100.90: 3개 (/.env · /wp-login.php · /phpmyadmin 404) → 탐색
  - 나머지 3개는 주소마다 1번씩입니다.
  - 다만 주소는 사람이 아니라 접속한 곳입니다. 한 주소를 여러 사람이 쓸 수도 있으니 "같은 사람"이 아니라 "같은 접속 지점"이 반복했다고 읽어야 합니다.

## 6교시 · 실패를 사용자별 · 시간대별로 묶어 세고 저장하기

### 문제 6-1 · 실패한 이벤트를 사용자별 · 시간대별로 묶어 세고 CSV 로 저장하기

- (가) 실행한 출력 전체를 붙여 넣고, 실패가 가장 많은 사용자와 횟수, 실패가 가장 많이 난 시간대와 횟수, 저장된 행 수를 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 실패가 가장 많은 사용자와 횟수 ③ 가장 많이 난 시간대와 횟수 ④ 저장된 행 수
  - 답:

```
--- 단계 1: 사용자별 실패 횟수
user
dami       4
gaeun      3
seoyeon    2
jiwoo      1
dtype: int64
--- 단계 2: 시간대별 실패 횟수
hour
2      1
9     13
10     3
11     5
18     1
dtype: int64
--- 단계 3: 저장한 파일 failed_events.csv
저장된 행 23 개
```

  - ② 실패가 가장 많은 사용자: dami 4번
  - ③ 실패가 가장 많이 난 시간대: 9시 13번
  - ④ 저장된 행 23개

- (나) 🔍 시간대별 결과에서 실패가 가장 많이 난 시간대의 개수를 보세요. 이 개수는 5교시 단계 3의 어느 소스 개수와 같은가요? 그 실패가 어느 소스에서 났는지 적고(근거는 숫자가 같다는 것까지 쓰면 됩니다), 이어서 확인할 것도 적어 주세요.

  - 쓸 내용: ① 많이 난 실패가 어느 소스에서 난 것인지와 그 근거 ② 이어서 확인할 것
  - 답: ① 많이 난 실패가 어느 소스에서 난 것인지와 그 근거
  - 실패가 가장 많은 시간대는 9시, 13개입니다. 이 개수는 5교시 단계 3의 web 실패 13개와 같습니다. 그래서 9시 실패는 web 소스에서 난 것으로 볼 수 있습니다.
  - 확정하려면 `failed_events.csv` 에서 `hour` 가 9인 행의 `source` 를 보면 됩니다. 실제로 13개 모두 `web` 입니다. web 샘플 로그는 모두 09:01 ~ 09:36 사이 기록입니다. server 실패는 10 · 11 · 18시, saas 실패는 2시에 났습니다.
  - ② 이어서 확인할 것
  - 9시 실패 13개를 ip 별로 나눠 봅니다. 그러면 203.0.113.50 이 7개(로그인 401 ×5, /admin 403 ×2)이고, 198.51.100.90 이 3개(/.env 등 404 탐색)입니다.
  - 203.0.113.50 은 401 다섯 번 뒤에 로그인 302(성공 가능성)가 있었습니다. 그 뒤 이 주소나 계정으로 다른 소스(server · saas)에서 이상한 행동이 이어졌는지 시간순으로 엮어 봅니다(상관분석).
  - 9시가 원래 요청이 많은 출근 시간대인지도 함께 봅니다. 시간대별 전체 이벤트 수와 비교하는 것입니다. 개수만 보면 요청이 많은 시간대가 늘 위로 올라옵니다.
- (다) 🔍 사용자별 실패 횟수를 모두 더하면 실패한 이벤트 전체보다 적습니다. 몇 개가 모자라고 왜 모자란지 적어 주세요. 그리고 이 차이를 모르고 사용자별 숫자만 보면 어떤 잘못된 판단을 할 수 있을지도 적어 주세요.

  - 쓸 내용: ① 몇 개가 모자란지 ② 모자란 이유 ③ 모르고 넘어가면 생기는 잘못된 판단
  - 답: ① 몇 개가 모자란지
  - 사용자별 실패를 더하면 dami 4 + gaeun 3 + seoyeon 2 + jiwoo 1 = 10개입니다. 실패한 이벤트 전체는 23개라서 13개가 모자랍니다.
  - ② 모자란 이유
  - web 이벤트는 user 가 None(빈 값)입니다. 판다스는 사용자별로 묶어 셀 때 빈 값을 빼고 셉니다. 그래서 web 실패 13개가 통째로 빠졌습니다. 모자란 13개가 5교시의 web 실패 13개와 정확히 같다는 점이 근거입니다.
  - ③ 모르고 넘어가면 생기는 잘못된 판단
  - 사용자별 숫자만 보면 dami(4번)가 가장 큰 문제로 보입니다. 실제로 가장 많이 실패한 대상은 **web 의 203.0.113.50(7번)**입니다. 로그인 반복 실패 뒤 성공한 정황까지 있어서 가장 먼저 봐야 할 대상인데, 표에 아예 나오지 않습니다.
  - 「실패는 10건뿐」이라고 실제보다 작게 보고하게 됩니다.
  - 주소만 있고 사용자가 없는 외부 공격(무차별 대입, 경로 탐색)이 집계에서 사라지니, 내부 사용자 문제만 있는 것처럼 오해하게 됩니다.
  - 그래서 사용자별 합계가 전체와 맞는지 늘 대조하고, 빈 값이 몇 개인지 따로 세야 합니다. 판다스에서는 dropna=False 를 주거나 빈 값 개수를 따로 세면 됩니다.
